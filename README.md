# RSScript

**RSScript is a managed systems language for AI-era software.**

It is designed for code that may be generated by AI, but still needs to be reviewed, maintained, and trusted by humans.

```text
Easy by default.
Fast when local.
Reviewable by design.
Compiled through Rust.
```

RSScript is not “Rust with GC” and not “Python with types”.

It is a language experiment around one question:

> If AI can write hundreds of lines of code quickly, how can humans review that code safely?

---

## Why RSScript exists

AI has changed the bottleneck of software development.

Before AI:

```text
Writing code was expensive.
Reviewing code was manageable.
```

After AI:

```text
Generating code is cheap.
Reviewing generated code is expensive.
```

Most existing languages were designed for humans writing code by hand. RSScript is designed for a different workflow:

```text
AI writes code.
The compiler checks semantic boundaries.
Humans review the risk, not every line.
```

RSScript makes important behavior visible in source code and machine-readable diagnostics:

```text
mutation
retention
resource lifetime
local performance boundaries
managed/local transitions
public API changes
native/unsafe boundaries
```

---

## Core philosophy

RSScript is built around three layers.

### Managed by default

Most application code should be simple.

```rust
let user = User.load(id: read user_id)
let response = Response.ok(body: read user)
```

Managed values are easy to share, store, pass around, and place into long-lived object graphs.

This is the default model for:

```text
business logic
agent memory
configuration
caches
ASTs
request/response objects
application state
```

### Local when performance matters

Hot paths can opt into local exclusive values.

```rust
local scratch = Buffer.new(size: 4096)

with File.open(path: read path) as file {
    File.read_into(file: mut file, buffer: mut scratch)?
}
```

A local value is locally exclusive. It cannot be silently retained by managed objects or captured by managed closures.

This gives RSScript a clear performance path for:

```text
parser buffers
JSON decoding
CSV processing
agent prompt buffers
tool argument buffers
compiler scratch space
image/audio preprocessing
```

### Reviewable at the boundary

Function calls use named arguments and visible effects.

```rust
Cache.put(
    cache: mut cache,
    key: read key,
    value: read image,
)
```

If a function keeps a value after it returns, it must say so:

```rust
fn put(
    cache: mut Cache,
    key: read String,
    value: read Image,
) -> Unit
    effects(retains(key), retains(value))
```

A reviewer can immediately see:

```text
cache is modified
key is read and retained
value is read and retained
```

## The small model

RSScript tries to keep the core model small.

```text
let       default managed value
local     local exclusive value for performance-sensitive code
with      scoped resource lifetime
manage    move a local value into the managed runtime

read      parameter is inspected
mut       parameter is modified
take      parameter is consumed

fresh     returned value is newly created
retains   function may retain a parameter after return
```

These concepts are meant to map directly to questions reviewers ask:

```text
What mutates?
What gets retained?
What resource is opened?
What resource is closed?
What value is local?
Where does local data enter managed state?
What public behavior changed?
```

## Example

```rust
fn copy_file(input: read Path, output: read Path) -> Result<Unit, IOError> {
    local buffer = Buffer.new(size: 8192)

    with File.open_read(path: read input) as reader {
        with File.open_write(path: read output) as writer {
            while File.read_into(file: mut reader, buffer: mut buffer)? {
                File.write(file: mut writer, data: read buffer)?
                Buffer.clear(buffer: mut buffer)
            }
        }
    }

    return Ok(Unit)
}
```

This code makes the important boundaries explicit:

```text
input/output are read
buffer is local scratch space
reader/writer are scoped resources
read_into mutates reader and buffer
write mutates writer
resources close at the end of their with blocks
```

## Library design

RSScript libraries should follow this rule:

```text
Managed at the surface.
Local in the engine.
Reviewable at the boundary.
```

User-facing APIs should be simple:

```rust
let json = Json.parse(text: read body)?
```

Library implementations can use local scratch buffers internally:

```rust
local scratch = JsonScratch.new()

JsonLexer.lex_into(
    text: read text,
    tokens: mut scratch.tokens,
)?

JsonParser.parse_into(
    tokens: read scratch.tokens,
    nodes: mut scratch.nodes,
)?
```

Expert APIs may expose `*_into` forms for reuse and low-allocation paths.

## Semantic review

RSScript review is intended to be semantic, not purely textual.

```sh
rss review --diff base/ changed/
```

answers:

```text
What changed?
```

Examples:

```text
function now mutates a parameter
function now retains a value
fresh guarantee was removed
resource scope changed
native boundary was introduced
```

```sh
rss review --map generated.rss
```

answers:

```text
What do I actually need to read?
```

For AI-generated code, this is critical. If a file contains 400 generated lines, the reviewer should first see a review map:

```text
ENTRY POINTS
  run_agent

REVIEW REQUIRED
  update_cache      mutates shared state, retains(value)
  save_report       resource boundary
  charge_card       native boundary

FOLDABLE
  private pure helpers
  no retention
  no resources
  no local/manage boundary
```

RSScript does not eliminate human review. It moves human review up one semantic level.

## Compilation strategy

RSScript does not currently plan to build its own VM or native backend.

The planned compilation architecture is:

```text
RSScript source
  -> RSScript parser / checker / review metadata
  -> generated Rust source
  -> rustc
  -> executable or library
```

Rust is used as the backend and ecosystem bridge.

RSScript owns:

```text
syntax
semantic checks
effect system
managed/local/resource rules
diagnostics
review metadata
source mapping
core signatures
```

Rust/rustc owns:

```text
machine code
optimization
platform support
native linking
crate ecosystem
```

This is an architectural choice, not just a temporary shortcut.

RSScript’s core value is in the front end: reviewable semantics, not reinventing a lower-quality compiler backend.

## Current status

RSScript is experimental.

The current implementation is a Rust-based front-end prototype focused on:

```text
lexer
parser
semantic checking
structured diagnostics
review-oriented rules
review map metadata
Rust source lowering
runtime crate type surface
runtime-mediated managed handles
explicit ResourcePool runtime errors
source-span hooks for manage and ResourcePool borrow lowering
source map JSON for generated Rust packages
rustc diagnostic remapping through source maps
core `.rssi` interface signatures
CI gates for formatting, linting, tests, and generated Rust fixtures
golden tests for Rust lowering and source-map shape
```

The first milestone is not a production runtime.

The first milestone is a strong review-first checker that can validate the language model against real examples.

Current CLI surface:

```sh
rss check [--json] [--core] [--interface <file.rssi> ...] <file.rss>
rss check --explain <code>
rss fmt <file.rss>
rss review [--json] --diff <old.rss> <new.rss>
rss review [--json] --map <file-or-directory>
rss lower --rust <file.rss>
rss lower --rust <file.rss> --out-dir <directory>
rss remap-rustc [--json] <rsscript-source-map.json> <rustc-json-lines>
rss verify-rust [--json] <file.rss>
```

## Non-goals

RSScript is not trying to maximize syntax cleverness or type-system expressiveness.

It deliberately avoids:

```text
implicit conversions
user-defined operator overloading
hidden allocation boundaries
hidden retention behavior
macro-heavy metaprogramming
complex public signatures
Rust-style lifetime syntax
C++-style implicit magic
TypeScript-style type gymnastics
```

The goal is not to make code as short as possible.

The goal is to make code clear enough that humans and tools can review it reliably.

---

## Design summary

RSScript exists because AI can write code now.

Humans still need to understand it.

RSScript tries to make that possible by making semantic risk visible:

```text
managed by default
local when performance matters
resources scoped with with
retention declared with effects(retains)
review powered by semantic metadata
compiled through Rust
```

RSScript is a language for building software that AI can help write and humans can still trust.
