# RSScript Language Specification v0.4.4

Status: Draft / Implementation Candidate  
Version: 0.4.4  
Audience: language designers, compiler implementers, standard-library authors, review-tool authors  
Compatibility note: v0.4.4 is a field-access and review-tool clarification patch over v0.4.3. It does not replace the v0.3 semantic core.

---

# 0. Executive Summary

RSScript v0.4.4 is a **managed systems language for AI-era software**.

It is designed for code that may be generated by AI, but must still be reviewed, maintained, and operated by humans.

The design target remains:

```text
Easy by default.
Fast when local.
Reviewable by one canonical style.
```

RSScript is not "Rust with GC" and not "Python with types".

It is:

```text
a managed-first language
with an explicit local capability
and a review-first surface syntax.
```

v0.4.4 keeps the v0.3/v0.4 semantic core:

```text
let       = managed binding
local     = local exclusive binding
with      = scoped resource management
fresh     = caller chooses managed/local at creation point
manage    = move local value into managed runtime
resource  = deterministic cleanup object
managed -> local does not exist
```

v0.4.4 keeps the v0.4.3 scoped language boundary and clarifies partial local field access, nested field paths, indexed container access, and semantic review maps for newly generated code.

The following are **not part of the normative language specification**:

```text
Device / GPU APIs
Agent runtime APIs
ModelClient / Sandbox / ToolRegistry packages
kernel language design
```

They may exist as separate use-case documents or libraries:

```text
RSScript Use Case: Agents
RSScript Use Case: Compute / Device APIs
```

The core language stays general-purpose.

---

# 1. Why RSScript Exists

Most existing programming languages were designed for:

```text
human writes code
human reviews code
```

In AI-assisted development, this assumption breaks:

```text
AI code generation is cheap.
Human review is still expensive.
Review becomes the bottleneck.
```

RSScript optimizes not only for writing code, but for **reviewing generated code at scale**.

This leads to several non-negotiable design choices:

```text
explicit parameter effects
named arguments
no implicit conversions
no user-defined operator overloading
one canonical style
structured diagnostics
review-tool metadata
```

RSScript accepts slightly more verbosity in exchange for reduced ambiguity.

---

# 2. Design Principles

## 2.1 Ease by default

Simple programs should be written in managed style.

```rust
fn main() -> Unit {
    let image = Image.load(path: read "in.png")?
    Image.resize(image: mut image, width: 800, height: 600)
    Image.save(image: read image, path: read "out.png")?
    return Unit
}
```

The user does not need to understand ownership or manual memory management for ordinary code.

---

## 2.2 Fast when local

Performance-sensitive code can opt into local exclusive values.

```rust
mode: uses-local

fn process(path: read Path) -> Result<fresh Image, ImageError> {
    local image = Image.load(path: read path)?

    Image.resize(image: mut image, width: 800, height: 600)
    Image.normalize(image: mut image)

    return Ok(image)
}
```

Local values enable:

```text
static local mutation checking
escape analysis
stack or arena allocation
buffer reuse
clear managed boundary via manage
```

---

## 2.3 Reviewable by one canonical style

RSScript has one canonical surface syntax.

The same operation must not have multiple equivalent spellings.

Non-canonical:

```rust
save(image: image, path: output)
```

Canonical:

```rust
Image.save(image: read image, path: read output)
```

There are no script/review/performance syntax profiles.

---

## 2.4 No hidden behavior

RSScript forbids hidden conversions and hidden calls.

Forbidden:

```text
implicit conversion
auto-deref
auto-ref
implicit From / Into chains
user-defined operator overloading
getter magic
dynamic field creation
macro systems that hide control flow
```

If a conversion happens, it is visible.

```rust
let y: Int64 = Int64.from(value: x)
```

---

## 2.5 Public APIs are review contracts

A public API must expose the information a reviewer needs:

```text
argument names
argument types
data effects: read / mut / take
return freshness: fresh or managed
retention effects: retains(param)
guarantees: no_panic / noalloc / pure / no_block
unsafe/native boundaries
```

Public APIs must not rely on inference.

---

## 2.6 Diagnostics are part of the language

Compiler diagnostics are standardized.

They must be useful to both:

```text
human reviewers
AI repair agents
```

Each diagnostic has:

```text
stable error code
human summary
primary source span
causal chain
structured fixes
machine-readable JSON form
```

---

# 3. Version Delta: v0.4.3 -> v0.4.4

v0.4.4 is a clarification patch over v0.4.3.

It does not change the core model.

It tightens the field-level access rules introduced in v0.4.3 by defining two previously underspecified corner cases:

| Area | v0.4.3 | v0.4.4 |
|---|---|---|
| Nested field paths | "statically known field path" was underspecified | explicit longest-common-prefix disjointness rule |
| Prefix conflicts | whole-base conflict existed, nested prefix cases were implicit | prefix paths explicitly conflict |
| Handle fields in paths | handle field behavior defined but path termination needed clarity | handle fields terminate local-inline path analysis |
| Indexed container access | not specified | indexes do not participate in partial local access |
| Container element disjointness | not specified | `buffers[0]` and `buffers[1]` conflict in v0.4.x |
| Split element access | not specified | must use explicit library APIs such as `with_two_mut` / `split_at_mut` |
| Review tooling | revision diff only | `rss review --diff` for revisions and `rss review --map` for absolute review maps |
| AI-generated new files | not separately modeled | review maps classify entry points, must-review regions, foldable local computation, and unknown regions |

v0.4.4 keeps the v0.4.3 scope decision:

```text
Agent and device/GPU APIs are use-case libraries, not normative language scope.
```

v0.4.4 also keeps these earlier v0.4.2/v0.4.3 additions:

```text
omitted mode = managed-only
standard-library philosophy
.rssi interface model
controlled native core boundary
signature complexity budget
resource generics with explicit bounds
```

# 4. File Modes

RSScript has file-level semantic modes.

Mode describes **semantic capability**, not style.

There is one canonical style in all files.

---

## 4.1 Omitted mode

If a file has no mode declaration, it is treated as managed-only.

```rust
fn main() -> Unit {
    let user = User.load(id: read user_id)?
    return Unit
}
```

Equivalent to:

```rust
mode: managed
```

This lowers the entry cost for ordinary code.

---

## 4.2 `mode: managed`

```rust
mode: managed
```

Allowed:

```text
let bindings
class values
managed struct values
resource values through with
fresh functions
ordinary public APIs
```

Disallowed:

```text
local bindings
manage
take parameters
local closures
ResourcePool<T>
```

`mode: managed` is optional but may be used as an explicit promise.

---

## 4.3 `mode: uses-local`

Required if the file uses local capability.

```rust
mode: uses-local
```

Allowed in addition to managed features:

```text
local bindings
manage
take parameters
local closures
ResourcePool<T: Resource>
local containers
```

A file must declare `mode: uses-local` if it contains any of:

```text
local x = ...
manage x
parameter: take T
local closure
ResourcePool<T>
```

---

## 4.4 Imports across modes

A `mode: uses-local` file may import managed-only modules.

A managed-only file may import public APIs from `uses-local` modules as long as those public APIs do not expose local-only requirements.

Therefore, library internals may be local-first while public APIs remain managed-first.

Example:

```text
json/internal/parser.rss     mode: uses-local
json/json.rssi               public managed-first signatures
user/app.rss                 no mode declaration, managed-only
```

The user imports `json/json.rssi`, not the internal local implementation.

# 5. Type Kinds

RSScript v0.4.4 has three user-facing type declaration kinds:

```text
class
struct
resource
```

There is no `own struct`.

---

## 5.1 `class`

A `class` is a managed identity object.

```rust
class User {
    id: UserId
    name: String
}
```

Properties:

```text
always managed
has reference identity
may be shared
may be cyclic
fields are managed or copy
cannot be local
cannot be fresh
cannot be resource
```

---

## 5.2 `struct`

A `struct` is a value object.

```rust
struct Image {
    pixels: Buffer
    metadata: handle Map<String, String>
}
```

Properties:

```text
may be managed through let
may be local through local
may be returned fresh
has no observable pointer identity
fields may be inline or handle
```

Examples:

```rust
let image = Image.load(path: read path)?       // managed
local image = Image.load(path: read path)?     // local
```

---

## 5.3 `resource`

A `resource` is an object requiring deterministic cleanup.

```rust
resource File {
    fd: Int

    drop {
        OS.close(fd: fd)
    }
}
```

Properties:

```text
must be used through with or approved resource containers
cannot be managed
cannot be local through ordinary local binding in v0.4.4
cannot be returned as an ordinary value
cannot be stored in class or struct fields
cannot be captured by managed closures
```

Primary usage:

```rust
with File.open(path: read path) as file {
    File.write(file: mut file, data: read data)?
}
```

---

# 6. Field Model: Inline vs Handle

RSScript has an explicit field model.

Each field is either:

```text
inline
handle
```

This distinction is essential for local values, `fresh`, and `manage`.

---

## 6.1 Inline fields

A field is inline if it is stored inside its containing value.

Default inline fields:

```text
Copy fields
struct fields
```

Example:

```rust
struct Point {
    x: Float
    y: Float
}

struct Rect {
    origin: Point
    size: Point
}
```

If `Rect` is local, both `origin` and `size` are local inline subvalues.

---

## 6.2 Handle fields

A handle field stores a managed handle.

Fields of `class` type are always handles.

```rust
class User { ... }

struct Session {
    user: User          // class, therefore managed handle
}
```

A `struct` field can be explicitly made a handle:

```rust
struct Config {
    name: String
    rules: handle List<Rule>
}
```

Here:

```text
name  = inline field
rules = managed handle field
```

---

## 6.3 Why `handle T` exists

For `struct` types, the default field mode is inline.

```rust
struct Image {
    pixels: Buffer      // inline Buffer
}
```

Sometimes a struct should store a managed reference instead:

```rust
struct ImageView {
    pixels: handle Buffer
}
```

Difference:

```text
Buffer        = moves with the containing struct
handle Buffer = managed handle preserved across local/manage boundaries
```

---

## 6.4 Local structs may contain handle fields

A local struct can point to managed objects through handle fields.

```rust
local cfg = Config.load(path: read path)?
```

If `Config` is:

```rust
struct Config {
    name: String
    rules: handle List<Rule>
    workspace: Buffer
}
```

then:

```text
cfg is local
cfg.name is inline
cfg.workspace is inline local
cfg.rules is a managed handle
```

The runtime must trace `cfg.rules` while `cfg` is alive.

---

## 6.5 `manage` and handle fields

When a local value is moved into managed runtime:

```rust
let shared = manage cfg
```

the runtime:

```text
recursively migrates inline local fields
preserves existing handle fields
does not deep-clone managed handles
marks the local binding as moved
```

For the `Config` example:

```text
cfg shell       -> migrated
cfg.name        -> migrated
cfg.workspace   -> migrated
cfg.rules       -> same managed handle
```

---

## 6.6 Resource fields

Resource fields are not allowed in ordinary `class` or `struct`.

Illegal:

```rust
struct Logger {
    file: File       // error: resource field
}
```

Use `with` or `ResourcePool<T: Resource>`.

---

# 7. Bindings

## 7.1 `let`

`let` creates a managed binding for non-Copy values.

```rust
let image = Image.load(path: read path)?
```

For non-Copy structs:

```text
let x = ... means managed x
```

For Copy values:

```rust
let count = 0
```

the value is copied normally.

---

## 7.2 `local`

`local` creates a local exclusive binding.

```rust
local image = Image.load(path: read path)?
```

A local binding:

```text
has exactly one local owner
can be passed as read
can be passed as mut with explicit mut
can be passed as take with explicit take
can be moved into managed runtime with manage
cannot be stored in managed objects
cannot be captured by managed closures
```

`local` is allowed only in `mode: uses-local`.

---

## 7.3 `with`

`with` introduces a scoped resource binding.

```rust
with File.open(path: read path) as file {
    File.write(file: mut file, data: read data)?
}
```

The resource is dropped when the block exits.

`with` is allowed in both file modes.

---

# 8. Managed and Local Worlds

RSScript has one default world and one local capability.

```text
managed = default world
local   = explicit capability
```

---

## 8.1 Managed values

Managed values:

```text
may be shared
may be stored
may be cyclic
may be mutated dynamically
are traced by the runtime
do not require local mutation markers for memory safety
```

Even in canonical syntax, `read` and `mut` are review-visible effects, not pointer syntax.

---

## 8.2 Local values

Local values:

```text
are exclusive within their scope
are checked statically for mut/take use
may be optimized aggressively
cannot be retained by managed objects
```

Local values require explicit call-site effects:

```rust
Image.resize(image: mut image, width: 800, height: 600)
```

---

## 8.3 Managed -> local does not exist

There is no conversion from managed to local.

Illegal:

```rust
let image = Image.load(path: read path)?
local working = image       // error
```

Reason:

```text
managed values may have arbitrary aliases
extracting an exclusive local value would be unsafe or require deep clone
```

Correct pattern:

```rust
local image = Image.load(path: read path)?
```

Choose local at creation time.

---

## 8.4 Deep clone is explicit and library-defined

RSScript does not provide a generic `to_local` or `owned_copy`.

If a type supports deep cloning into local form, it must expose an explicit API:

```rust
local image = Image.deep_clone_to_local(image: read managed_image)?
```

The name must make copying cost obvious.

---

# 9. Data Effects

Data effects describe how a function uses a parameter.

RSScript v0.4.4 has exactly three data effects:

```text
read
mut
take
```

There is no `share` data effect.

Retention is expressed by `effects(retains(param))`.

---

## 9.1 `read`

A `read` parameter may be inspected but not mutated and not retained unless `retains(param)` is present.

Signature:

```rust
fn hash(data: read Bytes) -> UInt64
```

Call:

```rust
hash(data: read bytes)
```

---

## 9.2 `mut`

A `mut` parameter may be modified during the call.

Signature:

```rust
fn resize(image: mut Image, width: Int, height: Int) -> Unit
```

Call:

```rust
Image.resize(image: mut image, width: 800, height: 600)
```

For managed arguments:

```text
mutation is dynamically shared
aliases observe the change
```

For local arguments:

```text
call site must use mut
compiler checks exclusive mutable access
```

---

## 9.3 `take`

A `take` parameter consumes a local value.

Signature:

```rust
fn consume(buffer: take Buffer) -> Unit
```

Call:

```rust
consume(buffer: take buffer)
```

After the call:

```rust
use(buffer)      // error: moved
```

`take` is allowed only in `mode: uses-local`.

A managed value cannot be passed to `take`.

---

## 9.4 Copy parameters

Copy parameters do not require data effects.

```rust
fn resize(image: mut Image, width: Int, height: Int) -> Unit
```

`width` and `height` are Copy.

At the call site:

```rust
Image.resize(image: mut image, width: 800, height: 600)
```

---

# 10. Field-Level Effects and Partial Local Access

v0.4.4 defines field-level effects so implementations can check local struct fields without importing Rust-style lifetime syntax.

This section is intentionally conservative.

The goal is:

```text
allow obvious disjoint inline struct fields
reject ambiguous whole-base, prefix, handle, and container element cases
```

---

## 10.1 Call-scoped access

`read`, `mut`, and `take` effects are call-scoped unless a function declares retention.

Example:

```rust
Stats.update(stats: mut report.stats, sample: read sample)
Summary.render(report: read report)
```

The `mut report.stats` access ends when `Stats.update` returns.

---

## 10.2 Place paths

A **place path** is a path used as an argument position.

Examples:

```text
state
state.inner
state.inner.cache
state.inner.buffer
state.buffers[0]
state.cache.entries
```

A **local-inline field path** is a place path that:

```text
starts from a local binding
contains only field accesses
passes only through inline fields
contains no handle field
contains no indexed container access
```

Examples of local-inline field paths:

```text
state.inner.cache
state.inner.buffer
state.parser.tokens
```

Not local-inline field paths:

```text
state.cache.entries      // if cache is a handle field
buffers[0]               // indexed container access
state.buffers[0].data    // indexed container access appears in the path
```

---

## 10.3 Managed base values

For managed base values, field effects use dynamic managed semantics.

```rust
let agent = Agent.new()
AgentMemory.append(memory: mut agent.memory, message: read msg)
Agent.inspect(agent: read agent)
```

Aliases may observe mutation.

No local partial-disjointness guarantee is made for managed bases.

---

## 10.4 Local inline field access

For a local struct value, an inline field may be accessed independently if the field path is statically known and local-inline.

Example:

```rust
mode: uses-local

local parser = ParserState.new()

TokenBuffer.clear(tokens: mut parser.tokens)
Arena.reset(arena: mut parser.arena)
```

The fields `tokens` and `arena` are disjoint inline fields.

---

## 10.5 Disjoint nested field paths

Two local-inline field paths are **disjoint** if:

```text
1. they have the same local base binding;
2. both paths contain only inline field accesses;
3. neither path is a prefix of the other;
4. after their longest common prefix, the next field component differs.
```

This means disjointness is determined by the first field component after the longest common prefix.

Allowed:

```rust
Foo.run(
    x: mut state.inner.cache,
    y: mut state.inner.buffer,
)
```

Paths:

```text
state.inner.cache
state.inner.buffer
```

Longest common prefix:

```text
state.inner
```

Next field components:

```text
cache vs buffer
```

They differ, so the paths are disjoint.

Also allowed:

```rust
Foo.run(
    x: mut state.parser.tokens,
    y: mut state.codegen.output,
)
```

Here the paths diverge immediately after `state`.

---

## 10.6 Prefix conflicts and whole-base conflicts

If one local-inline path is a prefix of another, the paths conflict.

Illegal:

```rust
Foo.run(
    x: mut state.inner,
    y: mut state.inner.cache,
)
```

Reason:

```text
state.inner is a whole prefix of state.inner.cache
```

A read of a whole base or whole prefix also conflicts with a mutable access to any subpath below it.

Illegal:

```rust
Foo.run(
    x: read state.inner,
    y: mut state.inner.cache,
)
```

Illegal:

```rust
Foo.run(
    x: read state,
    y: mut state.inner.cache,
)
```

Correct patterns:

```rust
let should_update = Foo.should_update(state: read state)
Foo.update_cache(cache: mut state.inner.cache)
```

or split state into explicit fields.

---

## 10.7 Handle fields in paths

A handle field is a managed handle stored inside a struct.

Handle fields terminate local-inline path analysis.

If a place path reaches a handle field, all access after that field is treated as managed access, not local inline access.

Example:

```rust
struct State {
    cache: handle Cache
}
```

For a local `state`, this is not a local-inline partial access:

```rust
Foo.run(
    x: mut state.cache.entries,
    y: mut state.cache.stats,
)
```

The compiler must not infer disjointness between `entries` and `stats` through the managed handle `state.cache`.

Allowed managed-handle access:

```rust
Cache.clear(cache: mut state.cache)
```

Rules:

```text
handle fields may be read
handle fields may be passed as mut to managed APIs
handle fields may not be taken
handle field mutation does not move the local base
```

Illegal:

```rust
take state.cache
```

---

## 10.8 Indexed container access

Indexed container access does not participate in local partial-disjointness in v0.4.x.

Any place path containing an index operation is treated as access to the whole container for local alias checking.

This includes literal indices and variable indices.

Illegal in v0.4.x:

```rust
mode: uses-local

local buffers = LocalVec<Buffer>.new()

Foo.run(
    a: mut buffers[0],
    b: mut buffers[1],
)
```

Illegal:

```rust
Foo.run(
    a: read buffers,
    b: mut buffers[0],
)
```

Illegal:

```rust
Foo.run(
    a: mut state.buffers[0],
    b: mut state.buffers[1],
)
```

Rationale:

```text
RSScript v0.4.x does not prove index inequality.
Even literal indices are not special-cased.
Container element disjointness must be expressed through explicit library APIs.
```

---

## 10.9 Explicit split APIs

Container libraries may provide explicit APIs that prove or check disjoint element access.

Such APIs must make the split boundary visible in source code.

Examples:

```rust
LocalVec.with_two_mut(
    vec: mut buffers,
    first: 0,
    second: 1,
    f: noescape Fn(a: mut Buffer, b: mut Buffer) -> Unit,
)
```

or:

```rust
LocalVec.split_at_mut(
    vec: mut buffers,
    index: split,
    f: noescape Fn(left: mut LocalSlice<Buffer>, right: mut LocalSlice<Buffer>) -> Unit,
)
```

These APIs may:

```text
perform runtime index checks
prove disjointness internally
return noescape temporary views
```

The language core does not infer disjointness for indexed access.

---

## 10.10 Moving the base

A local base cannot be `manage`d or `take`n inside the same expression where one of its fields is accessed.

Illegal:

```rust
Foo.run(
    cfg: read (manage config),
    workspace: mut config.workspace,
)
```

Split into separate statements.

---

## 10.11 Implementation note

An implementation may initially reject some valid disjoint-field cases.

However, it must not accept cases that violate:

```text
whole-base conflict
prefix conflict
handle-field boundary
indexed-container conflict
move-base conflict
```

# 11. Runtime Effects and Guarantees

v0.4.4 uses a **reductive effect model**.

Instead of declaring everything a function may do, functions declare guarantees about what they will not do.

Default assumption:

```text
a function may allocate
a function may panic
a function may block
a function may perform I/O
```

Source-level effects express constraints and special behavior.

---

## 11.1 Effect syntax

```rust
fn hash(data: read Bytes) -> UInt64
    effects(noalloc, no_panic, pure)
{
    ...
}
```

---

## 11.2 Standard guarantees

| Effect | Meaning |
|---|---|
| `no_panic` | function will not intentionally panic |
| `noalloc` | function performs no heap allocation |
| `no_block` | function does not block the current isolate |
| `pure` | no observable external side effects and no mutation of reachable managed state |
| `unsafe` | function contains or exposes unsafe behavior |
| `native` | function crosses native implementation boundary |
| `retains(x)` | function may retain parameter `x` after returning |

---

## 11.3 `pure`

A `pure` function:

```text
does not mutate managed state
does not perform I/O
does not retain parameters
does not depend on mutable global state
```

A `pure` function may allocate unless also marked `noalloc`.

---

## 11.4 `retains(x)`

`retains(x)` means the function may keep a managed reference derived from parameter `x` after the call returns.

Example:

```rust
fn cache_put(cache: mut Cache, key: read String, value: read Image) -> Unit
    effects(retains(value))
{
    Cache.insert(cache: mut cache, key: read key, value: read value)
}
```

The parameter remains `read` because it is only inspected during the call. Retention is post-call behavior and belongs in `effects`.

---

## 11.5 Passing local values to retaining APIs

A local value cannot be retained directly.

Illegal:

```rust
mode: uses-local

local image = Image.load(path: read path)?

cache_put(
    cache: mut cache,
    key: read key,
    value: read image,
)
```

Correct:

```rust
cache_put(
    cache: mut cache,
    key: read key,
    value: read (manage image),
)
```

---

## 11.6 `may_fail` is not an effect

Failure is represented by the return type.

```rust
fn load(path: read Path) -> Result<fresh Image, ImageError>
```

---

## 11.7 `async` is not an effect

`async` is part of the function kind.

```rust
async fn fetch(url: read Url) -> Result<fresh Bytes, NetworkError>
```

Async execution semantics are not defined in v0.4.4.

---

# 12. Function Signatures

## 12.1 Public functions

Public functions must have explicit:

```text
parameter names
parameter types
parameter data effects for non-Copy parameters
return type
guarantee effects if any
```

Example:

```rust
pub fn resize(image: mut Image, width: Int, height: Int) -> Unit
    effects(no_panic)
```

---

## 12.2 Private functions

Private functions follow the same canonical syntax.

Limited local variable type inference is allowed.

Function signatures are explicit.

---

## 12.3 Return modes

For non-Copy returns:

```text
T                 = managed T
fresh T           = fresh struct shell
Result<T,E>       = managed T on success
Result<fresh T,E> = fresh struct shell on success
```

Example:

```rust
fn lookup(cache: read Cache, key: read String) -> Option<Image>
```

Returns a managed `Image` because it comes from cache.

```rust
fn load(path: read Path) -> Result<fresh Image, ImageError>
```

Returns a fresh `Image`.

---

## 12.4 Signature complexity budget

Public signatures should be reviewable in one screen.

Implementations should lint:

```text
too many generic parameters
too deeply nested return types
too many effects
overly long where/requires clauses
ambiguous type aliases in public APIs
```

Recommended public API shape:

```rust
pub fn run(
    state: mut State,
    input: read Input,
) -> Result<fresh Output, RunError>
```

Discouraged:

```text
large Rust-style generic signatures
lifetime-like parameters in public APIs
nested type gymnastics
```

---

# 13. Named Arguments

RSScript uses named arguments as canonical call syntax.

## 13.1 Rule

All non-receiver arguments must be named.

```rust
Image.resize(image: mut image, width: 800, height: 600)
```

Illegal:

```rust
Image.resize(mut image, 800, 600)
```

There are no profile-dependent exceptions.

---

## 13.2 Names prevent AI mistakes

Correct:

```rust
Bank.transfer(from: mut source, to: mut target, amount: money)
```

Wrong argument order is less likely because names are visible.

---

## 13.3 Constructors

Constructors use named fields.

```rust
let point = Point(x: 1.0, y: 2.0)
```

---

## 13.4 Namespaces and functions

RSScript permits namespaced functions:

```rust
Image.load(path: read path)
File.open(path: read path)
```

Dot syntax is namespace access, not method dispatch magic.

No implicit receiver conversion occurs.

---

# 14. Calls and Effects

## 14.1 Read call

```rust
Image.save(image: read image, path: read output)
```

---

## 14.2 Mutating call

```rust
Image.resize(image: mut image, width: 800, height: 600)
```

---

## 14.3 Taking call

```rust
Buffer.consume(buffer: take buffer)
```

---

## 14.4 Managing local at call site

```rust
Cache.store(cache: mut cache, image: read (manage image))
```

# 15. `fresh`

`fresh T` means the returned top-level struct shell is newly created and has no aliases.

`fresh` is shallow.

It does not mean every internal handle is unique.

---

## 15.1 Valid fresh return types

`fresh` may be used only with `struct` types.

Legal:

```rust
fn load(path: read Path) -> Result<fresh Image, ImageError>
```

Illegal:

```rust
fn current_user() -> fresh User     // error if User is class
```

Resources are not fresh values.

---

## 15.2 Caller selects mode

```rust
let image = Image.load(path: read path)?       // managed
local image = Image.load(path: read path)?     // local
```

---

## 15.3 Shallow freshness

Example:

```rust
struct Pair {
    left: handle Image
    right: handle Image
}

fn pair(left: read Image, right: read Image) -> fresh Pair {
    return Pair(left: read left, right: read right)
}
```

The `Pair` shell is fresh.

The images inside it are managed handles and may be shared.

---

# 16. Fresh-Preservation Analysis

A function declared as returning `fresh T` must pass compiler freshness checking.

The analysis is intra-procedural.

Inter-procedural facts are taken only from function signatures.

---

## 16.1 Fresh expression sources

An expression is fresh if it is one of:

```text
struct constructor expression creating a new shell
call to a function returning fresh T
clean local binding
composition of fresh fields into a fresh shell
```

---

## 16.2 Clean local binding

A local binding is clean if it has not been:

```text
managed with manage
stored into a managed object or container
captured by a managed closure
passed to a function that retains it
moved by take
returned previously
assigned into a handle field
```

---

## 16.3 Fresh analysis pseudocode

```text
is_fresh(expr):
    match expr:
        StructLiteral(fields):
            return all field rules are valid for shallow fresh shell

        Call(f, args):
            return f.return_mode == fresh

        LocalVar(x):
            return is_clean_local(x)

        ManagedVar(_):
            return false

        FieldAccess(base, field):
            if field is handle:
                return false
            if base is clean local and field is inline:
                return true subject to move rules
            return false

        ContainerLookup(_):
            return false

        GlobalLookup(_):
            return false
```

---

## 16.4 Branches

All return branches must return fresh values.

Illegal:

```rust
fn make(cond: Bool, cache: read Cache) -> fresh Image {
    if cond {
        return Image.new(width: 1, height: 1)
    } else {
        return Cache.get(cache: read cache, key: read "default")
    }
}
```

The second branch returns an existing managed value.

---

## 16.5 Closures and freshness

A local captured by a managed closure is not clean.

A local temporarily used by a noescape closure remains clean if not retained.

```rust
mode: uses-local

noescape_apply(callback: noescape Fn())

local image = Image.load(path: read path)?

noescape_apply(callback: || {
    Image.inspect(image: read image)
})

return image      // still fresh if no retention occurred
```

---

## 16.6 Generics and freshness

A generic function returning `fresh T` must require `T: Struct`.

```rust
fn make_default<T: Struct>() -> fresh T
```

If freshness cannot be proven for all valid instantiations, the function is rejected.

---

# 17. `manage`

`manage` moves a local value into the managed runtime.

```rust
local image = Image.load(path: read path)?
let shared = manage image
```

After `manage`:

```rust
Image.save(image: read image, path: read output) // error
```

---

## 17.1 Semantics

`manage x`:

```text
requires x to be local
requires no active mut/take use
recursively migrates inline local graph into managed heap
preserves handle fields
returns managed handle
marks x as moved
may allocate
may abort current isolate on allocation failure
```

---

## 17.2 Failure

If migration allocation fails:

```text
the current isolate aborts
no rollback is guaranteed
no broken state is exposed
```

Transactional `manage` is not part of v0.4.4.

---

## 17.3 Cost

`manage` is not guaranteed O(1).

Cost is proportional to the local inline graph migrated.

Handle fields are not deep-cloned.

---

# 18. Resources and `with`

Resources require deterministic cleanup.

Primary usage:

```rust
with File.open(path: read path) as file {
    File.write(file: mut file, data: read data)?
}
```

---

## 18.1 Drop points

A `with` resource is dropped on:

```text
normal block exit
return
break
continue
panic unwind, if implementation supports unwinding
```

---

## 18.2 Resource escape is forbidden

Inside a `with` block, the resource cannot be:

```text
returned
managed
taken out of the block
stored in a managed object
captured by a managed closure
```

Illegal:

```rust
with File.open(path: read path) as file {
    return file
}
```

Illegal:

```rust
with File.open(path: read path) as file {
    let x = manage file
}
```

---

## 18.3 ResourcePool

v0.4.4 includes a standard-library escape hatch for long-lived resources.

```rust
ResourcePool<T: Resource>
```

`ResourcePool` is a privileged standard-library type.

It may hold resource values internally.

User-defined `class` and `struct` types may not directly contain resources.

Example:

```rust
mode: uses-local

local pool = ResourcePool<DbConnection>.new(
    create: || DbConnection.open(url: read url),
    max_size: 16,
)

with ResourcePool.borrow(pool: mut pool) as conn {
    DbConnection.query(conn: mut conn, sql: read sql)?
}
```

Rules:

```text
ResourcePool itself must be local
ResourcePool is allowed only in mode: uses-local
borrow returns a with-compatible resource lease
pool drop releases all held resources
resource values cannot escape the pool lease
```

---

# 19. Containers

## 19.1 Managed containers

Ordinary containers are managed.

```rust
let images = List<Image>.new()
```

Managed containers may store:

```text
Copy values
managed handles
managed structs
```

They cannot store local values directly.

To store a local value:

```rust
List.push(list: mut images, value: read (manage image))
```

---

## 19.2 Local containers

Local containers are advanced standard-library types.

```rust
mode: uses-local

local buffers = LocalVec<Buffer>.new()
```

Local containers may hold local struct values.

They cannot be managed directly unless explicitly converted with `manage`, which migrates their inline graph.

---

## 19.3 Resource containers

Only approved resource containers may store resources.

In v0.4.4:

```text
ResourcePool<T: Resource>
```

is the standard resource container.

---

# 20. Generics

## 20.1 Default bound

Generic type parameters default to `Managed`.

```rust
fn first<T>(items: read List<T>) -> Option<T>
```

means:

```rust
fn first<T: Managed>(items: read List<T>) -> Option<T>
```

`T: Managed` may be:

```text
Copy
class handle
managed struct handle
```

Resource types are not `Managed`.

---

## 20.2 Struct bound

Use `T: Struct` for fresh or local-capable values.

```rust
fn make_pair<T: Struct>(left: read T, right: read T) -> fresh Pair<T>
```

---

## 20.3 Resource bound

Resource generic APIs must be explicit.

```rust
ResourcePool<T: Resource>
```

Ordinary `List<T>` cannot be instantiated with a resource type.

---

## 20.4 Generic resource declarations

A `resource` type may have type parameters.

Example:

```rust
resource NativeHandle<T: Managed>
```

Rules:

```text
type parameters must be explicitly bounded
unbounded resource type parameters are forbidden
resource type parameters do not make the resource managed
resource values still require with or approved resource containers
```

A generic resource may be used for native/runtime handles whose behavior depends on an element type, descriptor type, or protocol type.

---

## 20.5 Resource type parameters

A generic resource may not contain another resource type parameter unless it is an approved resource container.

Allowed:

```rust
ResourcePool<T: Resource>
```

Potentially allowed by core/runtime libraries:

```rust
resource BufferLease<T: Managed>
```

Disallowed for ordinary user code:

```rust
resource BoxedResource<T: Resource> {
    inner: T
}
```

Reason:

```text
general nested resource ownership requires more advanced drop composition rules
```

---

## 20.6 Drop for generic resources

A generic resource must have a drop implementation valid for all allowed type parameters.

Drop may rely on:

```text
resource's own fields
runtime descriptors supplied by the implementation
explicit type bounds
```

Drop must not depend on implicit reflection or hidden type-specific behavior.

---

## 20.7 Retention with generics

A function retaining a generic parameter must declare it:

```rust
fn store<T: Managed>(box: mut Box<T>, value: read T) -> Unit
    effects(retains(value))
```

---

# 21. Closures

RSScript has three closure categories.

```text
managed closure
local closure
noescape closure
```

---

## 21.1 Managed closure

A closure bound with `let` is managed.

```rust
let callback = || {
    Log.info(message: read "done")
}
```

Managed closures may capture:

```text
Copy values
managed values
```

They may not capture:

```text
local values
resources
with-bound resources
```

---

## 21.2 Local closure

A closure bound with `local` is local.

```rust
mode: uses-local

local buffer = Buffer.new(size: 1024)

local callback = move || {
    Buffer.clear(buffer: mut buffer)
}
```

Local closures may move-capture local values.

---

## 21.3 Noescape closure

A noescape closure cannot be stored or returned.

```rust
fn apply(callback: noescape Fn()) -> Unit
```

Noescape closures may temporarily use local values.

```rust
mode: uses-local

local image = Image.load(path: read path)?

apply(callback: || {
    Image.inspect(image: read image)
})
```

---

# 22. Error Handling

RSScript uses explicit result types for recoverable errors.

```rust
Result<T, E>
Option<T>
```

`may_fail` is not a runtime effect.

Example:

```rust
fn load(path: read Path) -> Result<fresh Image, ImageError>
```

Use of `?` is allowed only inside functions returning compatible `Result`.

---

## 22.1 Panic

Panic is unrecoverable by default.

Functions may panic unless marked `no_panic`.

```rust
fn parse(input: read String) -> Result<fresh Ast, ParseError>
    effects(no_panic)
```

---

## 22.2 Exhaustive matching

Pattern matches must be exhaustive.

Wildcard patterns in public code are discouraged and may be linted.

---

# 23. Forbidden Features

RSScript v0.4.4 does not support:

```text
implicit conversion
auto-deref
auto-ref
implicit From / Into chains
user-defined operator overloading
dynamic field creation
monkey patching
custom getter/setter magic
public API type inference
overloaded functions by argument type
macros that hide control flow
method dispatch that changes field-access semantics
borrow-returning public APIs
managed -> local demotion
generic owned_copy
own struct
surface &T / &mut T syntax
hidden resource finalizers
general user-defined FFI
```

---

## 23.1 Operators

Operators are limited to built-in types.

Allowed:

```text
numeric + - * /
boolean && ||
comparison for built-in comparable types
```

Disallowed:

```rust
matrix_a + matrix_b
money + tax
```

Use named functions:

```rust
Matrix.add(left: read a, right: read b)
Money.add(left: read price, right: read tax)
```

---

# 24. Standard Library Philosophy

RSScript libraries should follow:

```text
Managed at the surface.
Local in the engine.
Reviewable at the boundary.
```

---

## 24.1 User-facing APIs are managed-first

Default APIs should be simple.

```rust
let json = Json.parse(text: read body)?
```

The user should not need to manually construct scratch buffers for ordinary use.

---

## 24.2 Library implementations are local-first

Library internals should use local scratch values where appropriate.

Example:

```rust
mode: uses-local

pub fn parse(text: read String) -> Result<fresh JsonValue, JsonError> {
    local scratch = JsonScratch.new(
        token_capacity: 4096,
        node_capacity: 2048,
    )

    JsonLexer.lex_into(
        text: read text,
        tokens: mut scratch.tokens,
    )?

    JsonParser.parse_into(
        tokens: read scratch.tokens,
        nodes: mut scratch.nodes,
    )?

    local value = JsonBuilder.build(nodes: read scratch.nodes)?

    return Ok(value)
}
```

---

## 24.3 Expert APIs use `*_into`

Hot-path APIs should expose explicit destination buffers.

Examples:

```rust
File.read_into(file: mut File, buffer: mut Buffer) -> Result<Int, IOError>

Json.parse_into(
    text: read String,
    scratch: mut JsonScratch,
    output: mut JsonBuilder,
) -> Result<Unit, JsonError>
```

This pattern avoids hidden allocation and enables local buffer reuse.

---

## 24.4 Public APIs should prefer `fresh` for new values

If a function creates a new struct value, it should return `fresh T`.

```rust
Image.load(path: read Path) -> Result<fresh Image, ImageError>
Json.parse(text: read String) -> Result<fresh Json, JsonError>
```

If a function returns an existing shared object, it returns managed `T`.

```rust
Cache.get(cache: read Cache, key: read String) -> Option<Image>
```

---

## 24.5 Retention must be declared

Functions that store or retain parameters must declare `retains`.

```rust
List.push(list: mut List<T>, value: read T) -> Unit
    effects(retains(value))
```

---

## 24.6 Expensive clone APIs must be explicit

Avoid generic names like:

```text
to_local
owned_copy
localize
```

Prefer:

```text
deep_clone_to_local
clone_into_local
copy_pixels_to_local
```

---

# 25. Core Library Model

The core library may be developed signature-first.

This allows the checker and review tools to understand APIs before full implementations exist.

---

## 25.1 Interface files

Core packages may provide `.rssi` interface files.

Example:

```rust
// core/json/json.rssi

struct JsonValue

pub fn parse(text: read String) -> Result<fresh JsonValue, JsonError>

pub fn field_string(
    value: read JsonValue,
    name: read String,
) -> Result<String, JsonError>
```

The compiler may load `.rssi` files for type checking and review metadata.

---

## 25.2 Native implementation files

Early implementations may be written in Rust or another host language.

The RSScript interface remains authoritative.

```text
.rssi signature
    -> native implementation
    -> RSScript checker/runtime registry
```

The native implementation must obey the declared RSScript signature and effects.

---

## 25.3 Core and compiler versioning

During early development:

```text
compiler version == core interface version
```

Core APIs are unstable before the first beta.

---

## 25.4 Core MVP packages

A minimal core should include:

```text
Unit
Bool
Int
Float
String
Bytes
Buffer
Option<T>
Result<T,E>
List<T>
Map<K,V>
Set<T>
Path
File
ResourcePool<T: Resource>
Json
Diagnostic
Test
```

Agent, GPU, HTTP, and other domain libraries are not part of the language core specification.

They may be developed as packages.

---

## 25.5 Buffer genericity

The language specification does not require `Buffer` to be generic.

A standard library may choose one of several designs:

```text
Buffer          byte-oriented buffer
Buffer<T>       typed buffer, if the core library supports it
Bytes           immutable byte sequence
LocalVec<T>     local generic container
```

The language only requires that buffer APIs declare their data effects and retention behavior.

---

# 26. Native Core and FFI Boundary

v0.4.4 does not define a general user FFI.

It defines a controlled native boundary for core and runtime implementation.

---

## 26.1 `native`

A native function crosses the host implementation boundary.

```rust
native fn File.read_into(
    file: mut File,
    buffer: mut Buffer,
) -> Result<Int, IOError>
    effects(native)
```

Rules:

```text
native must be explicit
native signatures must include data effects
native signatures must include retention effects
native resource types must define cleanup
native errors must be converted into Result
native panic must not silently cross into RSScript
```

---

## 26.2 Native cannot violate local rules

Native code must not:

```text
retain local values unless they were managed
store local values in managed objects
return fake fresh values
capture local values in managed callbacks
allow resource escape from with
```

If native code needs to retain a value, the signature must declare `effects(retains(x))`.

---

## 26.3 Native handles

Native resources should be modeled as `resource`.

Example:

```rust
resource File
resource Socket
resource DbConnection
```

Native managed objects should be modeled as `class` or managed `struct` handles with explicit `handle` fields where needed.

---

## 26.4 External process bridges

External process or tool bridges are library patterns, not language-level FFI.

A library may expose a bridge through ordinary RSScript signatures:

```rust
pub fn ExternalProcess.run(
    command: read Command,
    input: read Bytes,
) -> Result<fresh Bytes, ProcessError>
```

The language specification does not define any agent-specific bridge API.

---

# 27. Semantic Review Tool

`rss review` is a semantic review tool.

It has two related but distinct jobs:

```text
1. diff review
   Compare two checked revisions and report what changed semantically.

2. absolute review map
   Analyze one checked program and report which parts require human review.
```

This distinction is important.

A diff review answers:

```text
What changed in this PR?
```

An absolute review map answers:

```text
This file is new or AI-generated. Which parts must I read first?
Which parts are low-risk enough to fold initially?
```

RSScript's review tooling exists because AI can generate hundreds of lines of code faster than humans can review them line by line.

The goal is not to remove human review.

The goal is to move human review up one semantic level.

---

## 27.1 `rss review --diff`

`rss review --diff` compares two checked RSScript revisions.

Example:

```sh
rss review --diff base/ changed/
rss review --diff base.rss changed.rss
```

It should report:

```text
public API changes
parameter effect changes
return freshness changes
retention changes
guarantee changes
new unsafe/native usage
new local/manage boundary
resource lifetime changes
new inferred allocations or panics, when detectable
callers requiring re-review
```

Example output:

```text
semantic diff:

  cache_put:
    effects: +retains(value)

  normalize:
    parameter image: read -> mut

  parse_config:
    return: Config -> fresh Config

  process_image:
    guarantee removed: noalloc
```

`--diff` is primarily for reviewing changes to existing code.

---

## 27.2 `rss review --map`

`rss review --map` analyzes a single checked file, module, or package.

Example:

```sh
rss review --map generated_handler.rss
rss review --map src/agent/
```

It produces a **review map**.

A review map partitions code into review regions:

```text
entry points
review-required functions
low-risk foldable functions
unknown / unresolved functions
```

The intended use case is AI-generated code with no useful old revision.

Example output:

```text
review map: handler.rss (412 lines)

  ENTRY POINTS (13 lines)
    main
    run_agent

  REVIEW REQUIRED (41 lines, 5 functions)
    save_report
      risk: high
      reasons: effects(retains(db)), resource/IO boundary

    update_cache
      risk: medium
      reasons: mut shared state, effects(retains(value))

    charge_card
      risk: high
      reasons: native boundary, resource/IO boundary

    parse_untrusted
      risk: medium
      reasons: may panic inferred, external input

    audit_log
      risk: medium
      reasons: resource/IO boundary

  LOW-RISK FOLDABLE (358 lines, 37 functions)
    private pure computations over inputs
    no retention
    no resources
    no local/manage boundary
    no native/unsafe boundary
```

`--map` is primarily for reviewing new AI-generated code.

---

## 27.3 Review map categories

### Entry points

Entry points are functions that define the external behavior of a file, module, package, command, test, or service.

Examples:

```text
main
exported public APIs
test functions
handler functions
agent loop functions
registered callbacks
```

Entry points should always be shown in the review map.

---

### Review-required functions

A function is review-required if it contains or exposes any semantic risk.

A function is review-required if it has any of:

```text
public API surface
mut parameter
read -> mut effect boundary
take parameter
manage operation
effects(retains(...))
resource usage through with
ResourcePool usage
native or unsafe effect
unknown native call
fresh guarantee boundary
removed or missing no_panic/noalloc guarantee in strict contexts
calls to review-required functions
unresolved calls or unknown effect summaries
writes to managed state
writes to handle fields
uses global state
```

Review-required does not mean wrong.

It means:

```text
a human reviewer should look here before trusting the generated code.
```

---

### Low-risk foldable functions

A function may be marked low-risk foldable if the checker can prove that it has no externally visible behavior except its return value.

A function is low-risk foldable only if:

```text
it is not an entry point;
it is not public, or public API review has already accepted the signature;
it has no mut parameters;
it has no take parameters;
it has no effects(retains(...));
it does not use with resources;
it does not call native or unsafe functions;
it does not call unknown functions;
it does not call review-required functions;
it does not use manage;
it does not store into managed objects or handle fields;
it does not mutate reachable managed state;
it does not capture local values in managed closures;
it is pure by declaration or inference.
```

If a function is low-risk foldable, the review tool may hide its body by default.

This does **not** mean the function is logically correct.

It means:

```text
reading this function is unlikely to reveal resource, mutation, retention,
managed/local boundary, or unsafe/native risk.
```

A reviewer may still inspect foldable functions for business logic correctness.

---

### Unknown / unresolved functions

A function is unknown or unresolved if the review tool cannot build a complete semantic summary.

Causes include:

```text
unresolved function call
missing core signature
missing native summary
unknown effect annotation
unsupported syntax
analysis limit exceeded
```

Unknown functions must not be folded into low-risk regions.

They should appear as review-required or unknown.

---

## 27.4 Semantic summary

`rss review` operates on function-level semantic summaries.

A function summary should include at least:

```text
function name
visibility
source line range
parameter names
parameter data effects
return type
return freshness
guarantee effects
retention effects
local bindings
manage operations
resource scopes
native/unsafe usage
calls
callees requiring review
freshness result
resource escape result
local escape result
```

The summary is used both by `--diff` and `--map`.

`--diff` compares summaries across revisions.

`--map` classifies summaries inside one revision.

---

## 27.5 Review map risk levels

`rss review --map` may classify functions by risk.

High risk:

```text
unsafe/native added or present
resource escape
public parameter read -> mut/take
take of local value
manage boundary
fresh guarantee removed or unproven on public API
new effects(retains(...)) on public API
unknown external call
```

Medium risk:

```text
new mut parameter
new resource scope
new ResourcePool use
new retention in private API
local value managed into long-lived state
noalloc/no_panic removed in strict contexts
pure guarantee missing where expected
```

Low risk:

```text
private pure helper
copy-only computation
constructor of fresh shell
formatting or naming-only change
private implementation with identical public effects
```

Risk levels are advisory.

A project may tune risk rules through lint configuration, but the default RSScript profile should be conservative.

---

`rss review --map --json` should emit structured review regions.

```json
  "summary": {
    "entry_point_lines": 13,
    "review_required_lines": 41,
    "foldable_lines": 358,
    "unknown_lines": 0
  }
}
```

The JSON form is intended for:

```text
IDE folding
AI repair agents
PR bots
risk dashboards
human review tools
```

---

## 27.7 What `--map` guarantees

`--map` is a review-prioritization tool.

It is not a proof of business correctness.

It can identify:

```text
where mutation occurs
where retention occurs
where resources are opened
where local values cross into managed state
where native or unsafe code is used
where freshness guarantees are asserted
where guarantees are missing or removed
```

It cannot decide:

```text
whether the algorithm is correct
whether a condition is logically reversed
whether a business policy is right
whether a prompt is well-written
whether a tool call is semantically appropriate
```

Therefore, RSScript review has two layers:

```text
semantic review:
  tool-assisted risk map and semantic diff

logic review:
  human inspection of business intent where needed
```

---

## 27.8 Relation between `--diff` and `--map`

`--diff` and `--map` should share the same semantic summary engine.

```text
rss check
  parses and checks code

rss review --map
  summarizes one checked program and classifies review regions

rss review --diff
  compares summaries from two checked programs
```

A complete implementation may expose all summaries through a common JSON protocol.

---

## 27.9 Minimum implementation requirement

The first implementation of `rss review --map` may be conservative.

A minimal implementation should:

```text
list all functions
mark public and entry functions as review-required
mark functions with mut/take/retains/manage/with/native/unsafe as review-required
mark functions with unresolved calls as unknown
mark private pure/no-retain/no-resource helpers as foldable
report line counts by category
emit JSON
```

It is acceptable for early implementations to over-report review-required code.

It is not acceptable to mark unknown or effectful code as foldable.

# 28. Diagnostics Protocol

Compiler diagnostics must have both human-readable and machine-readable forms.

---

## 28.1 Human form example

```text
error[RS0401]: `image` was moved into the managed runtime by `manage image`

  image.rss:12:18
    let shared = manage image
                 ^^^^^^^^^^^^ moved here

After `manage`, the local binding no longer exists.

help: move this use before `manage image`
help: if you need a separate managed value, use an explicit deep clone API
```

# 30. Isolate Model

RSScript v0.4.4 uses a single-isolate runtime model.

```text
each isolate owns one managed heap
managed values do not cross isolates
local values are isolate-local
resources are isolate-local
cross-isolate communication is future work
```

Future versions may add:

```text
Send
Share
channels
message passing
multi-isolate runtime
```

# 31. Examples

## 31.1 File write

```rust
fn write_text(path: read Path, text: read String) -> Result<Unit, IOError> {
    with File.open_write(path: read path) as file {
        File.write(file: mut file, data: read text)?
    }

    return Ok(Unit)
}
```

No mode declaration is needed because this file is managed-only.

---

## 31.2 Image pipeline

```rust
mode: uses-local

fn make_thumbnail(input: read Path, output: read Path) -> Result<Unit, ImageError> {
    local image = Image.load(path: read input)?

    Image.resize(image: mut image, width: 256, height: 256)
    Image.normalize(image: mut image)

    let shared = manage image

    Image.save(image: read shared, path: read output)?

    return Ok(Unit)
}
```

---

## 31.3 Cache retention

```rust
class ImageCache {
    entries: Map<String, Image>
}

fn cache_put(cache: mut ImageCache, key: read String, value: read Image) -> Unit
    effects(retains(value))
{
    Map.insert(map: mut cache.entries, key: read key, value: read value)
}
```

With local image:

```rust
cache_put(
    cache: mut cache,
    key: read key,
    value: read (manage image),
)
```

---

## 31.4 Local partial field access

```rust
mode: uses-local

struct ParserInner {
    cache: CacheState
    buffer: Buffer
}

struct ParserState {
    inner: ParserInner
    arena: Arena
}

fn step(state: mut ParserState) -> Result<Unit, ParseError> {
    Parser.advance(
        cache: mut state.inner.cache,
        buffer: mut state.inner.buffer,
        arena: mut state.arena,
    )?

    return Ok(Unit)
}
```

The paths `state.inner.cache`, `state.inner.buffer`, and `state.arena` are disjoint inline field paths.

Illegal because one path is a prefix of another:

```rust
Parser.advance(
    inner: mut state.inner,
    cache: mut state.inner.cache,
)
```

Illegal because a whole-prefix read conflicts with a mutable subpath:

```rust
Parser.advance(
    state: read state,
    cache: mut state.inner.cache,
)
```

---

## 31.5 Indexed container access is not partial

```rust
mode: uses-local

local buffers = LocalVec<Buffer>.new()

// error in v0.4.x
Foo.run(
    a: mut buffers[0],
    b: mut buffers[1],
)
```

Use an explicit container API:

```rust
LocalVec.with_two_mut(
    vec: mut buffers,
    first: 0,
    second: 1,
    f: || {
        // noescape body receives disjoint temporary views
    },
)
```

## 31.6 Config with handle fields

```rust
mode: uses-local

struct Config {
    name: String
    rules: handle List<Rule>

fn load_config(path: read Path) -> Result<fresh Config, ConfigError> {
    local workspace = Buffer.new(size: 4096)

        name: "default",
        rules: read rules,
        workspace: take workspace,

}
```

## 31.7 Resource pool

```rust
mode: uses-local

fn run_queries(url: read Url, queries: read List<Query>) -> Result<Unit, DbError> {
    local pool = ResourcePool<DbConnection>.new(
        create: || DbConnection.open(url: read url),
        max_size: 16,
    )

    for query in queries {
        with ResourcePool.borrow(pool: mut pool) as conn {
            DbConnection.query(conn: mut conn, sql: read query.sql)?
        }
    }

    return Ok(Unit)
}
```

# 32. Non-goals of v0.4.4

RSScript v0.4.4 does not attempt to support:

```text
multiple surface styles
Rust-like lifetime syntax
surface & / &mut
full ownership polymorphism
GC -> local demotion
moving GC
thread-shared managed heap
general resource fields
generic resource containers beyond approved standard types
operator-overloaded numeric DSLs
macro-heavy metaprogramming
implicit typeclass/trait dispatch
user-defined general FFI
GPU kernel language
agent runtime standard library
```

Agent and compute/device scenarios are important use cases, not normative language scope.

# 33. Implementation Notes

# 34. Reviewer Checklist

Reviewers should evaluate v0.4.4 by asking:

```text
1. Is the language spec scoped to the core language and tooling contract?
2. Are agent/GPU concepts outside the normative spec?
3. Is there exactly one canonical surface syntax?
4. Are file modes semantic rather than stylistic?
5. Does every public API expose data effects?
6. Are retention effects clearly expressed with retains(param)?
7. Is the reductive effect system understandable?
8. Are handle fields sufficiently clear?
9. Is field-level local access sufficiently specified?
10. Is generic resource behavior sufficiently specified?
11. Is fresh-preservation implementable?
12. Are resources usable through with and ResourcePool?
13. Are diagnostics structured enough for AI repair tools?
14. Does the language still feel easy in managed-only files?
15. Does local mode give a clear performance path?
16. Does `rss review --diff` capture semantic changes between revisions?
17. Does `rss review --map` reduce review surface for newly generated code?
```

# 35. Final Model Summary

RSScript v0.4.4 can be summarized as:

```text
one canonical syntax
optional managed-only file header
two file capabilities: managed-only and uses-local
three type kinds: class / struct / resource
three data effects: read / mut / take
reductive runtime guarantees
fresh at creation point
manage as one-way boundary
resources through with
retention through effects(retains)
nested field-level local access rules
indexed-container access is whole-container access
resource generics with explicit bounds
semantic semantic review tooling (`--diff` and `--map`) as part of the language
```

Or, shorter:

```text
Easy by default.
Fast when local.
Reviewable by one canonical style.
```
